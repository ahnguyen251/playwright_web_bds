# DOM & Selector Investigation Guide for Propify

When investigating UI elements, locators, and user flows on Propify:

## 1. Tool Routing

1. **Existing Page Objects First**:
   - Check `pages/` to see if a Page Object or Component already models the target surface.
   - Example: `pages/authentication/LoginPage.ts`, `pages/components/HeaderComponent.ts`, `pages/listings/ListingPage.ts`.
   - Never invent new duplicate locators if an existing Page Object already manages the element.

2. **Routes & Constants**:
   - Inspect `constants/routes.ts` for canonical application URL paths.
   - Inspect `constants/timeouts.ts` for standard wait thresholds.

3. **DOM Inspection Tools**:
   - Use `node dump_dom.js` or `node dump_labels.js` if available to dump interactive element trees.
   - When inspecting HTML snapshots or DOM traces, look for accessible roles (`button`, `heading`, `textbox`, `combobox`, `dialog`) and accessible names.

4. **Selector Precedence**:
   1. `page.getByRole(role, { name, exact })` — Best accessibility and semantic resilience.
   2. `page.getByPlaceholder(text, { exact })` — Ideal for input fields.
   3. `page.getByText(text, { exact })` — For static text, labels, alerts.
   4. `page.getByTestId(id)` — When data-testid is available.
   5. Scoped locators: `parentLocator.getByRole(...)` or `container.locator('...')`.
   6. **FORBIDDEN**: Fragile CSS classes generated by Tailwind or deep CSS selectors (`div > div:nth-child(2) > span`), arbitrary XPath (`//div[3]/button[1]`).

5. **Network & API Investigation**:
   - Check `helpers/network/` to observe network requests (e.g. `AuthRequestObserver`).
   - Check whether an action triggers an asynchronous API call (e.g. OTP send, search listing query) before asserting UI state.
